# Инструкции для Агента

- Файлы приложения находятся в папке `.app/`
	- Техническую документацию веди в `.app/docs/`
Документация которую ведёт исключительно основатель (Только для чтения) `docs/`

Если режим кодинга: Выполняешь техническое задание с DoD. Если нет технического задания с DoD – отказываешься выполнять задачу и даёшь предложение по DoD, спросив: "DoD должен в итоге выглядеть так? ..."

## Разработка
Техническая документация ведётся на английском языке.
- **Документируй код:**
    - Добавляй `///` (для `struct`, `enum`, `fn`, модулей) и `//!` (для файлов/крайних уровней) ко всем публичным элементам.
    - Описывай назначение, а также секции `Examples`, `Panics` и `Errors` при необходимости.
- **Проверяй документацию:**
    - После изменений всегда запускайте `cargo doc --no-deps` и устраняй любые предупреждения и ошибки компиляции доков (`missing_docs` и т.д.).
- **Защита от пропуска:**
    - Агент должен настроить в `Cargo.toml` (`[lints.rust] missing_docs = "warn"`) или через Git-хуки автоматическую проверку документации при сборке и коммитах.
## Если пользователь говорит что что-то не работает

- Ответь на вопросы: "Почему не получилось полноценно манифестировать визию пользователя? Где Мы друг-друга не поняли?".
- Заботливо спроси в чём конкретно помеха UX/UI и лаконично, нетехническим языком помоги пользователю объяснить Его точку зрения и составить сценарий UX/UI, а не навязывай что всё работает правильно.
- Утверди сценарий UX/UI.
- Действуй точечными шагами по сценарию без побочных эффектов.
- Делаешь одну вещь, доводишь с пользователем до идеала, покрываешь тестами, переходишь к следущей.

## Коммиты

После каждого ответа Агент обязан сделать атомарный коммит всех изменений, сделанных в ходе этого ответа, но если изменений нет – коммит не делать.

Правила коммита:

- Коммит должен быть атомарным: содержать только изменения, связанные с одним логическим заданием из ответа.
- Перед коммитом проверить `git status` и `git diff`, чтобы исключить лишние/случайные файлы.
- Сообщение коммита писать по agreement репозитория (кратко, по существу, на русском или английском).
- Не коммитить секреты, ключи, бинарные артефакты и файлы из `.gitignore`.
- Не делать `git push` без прямого запроса пользователя.

## Чек-лист перед любой правкой

Перед любым изменением кода определить:

**Она меняет архитектуру (хранилища, команды, ревизии и.т.д...)?** Тогда нужен ADR в `docs/DECISIONS/`, а не просто фикс.

**Декомпозиция бог-объектов и мега-компонентов:** стараться реализовывать «один файл — одна ответственность». Большой файл >500 строк с разной ответственностью режем на модули.

## Запуск и пересборку polygram

Если редактировали `polygram`, то после ответа обязательно закрывай и пересобирай его:

1. Закрыть `polygram.exe` (например, `Get-Process polygram | Stop-Process -Force`).
2. Собрать и запустить: `Start-Process powershell -ArgumentList "-Command cargo run -p polygram"`.
3. Убедиться, что процесс запущен (не failed) и окно видимо на экране. Если процесс упал — исправить ошибку не ломая приложение, собрать и запустить снова.
4. Сделать атомарный коммит изменений (см. правила выше). После коммита кратко сообщить пользователю хеш и сообщение коммита.
5. В самом конце выполнить: `Invoke-RestMethod -Uri "http://192.168.0.10:5000/signal" -Method Post -ContentType "application/json" -Body '{"title": "Agent", "message": "Ready."}'`
   - Всегда вызывать напрямую в PowerShell, не оборачивать в `powershell -Command "..."`.

После каждого ответа приложение должно оставаться запущенным и висеть на экране после отправки сигнала — не закрывать его, оно будет работать до тех пор, пока следущий Агент или пользователь сами не закроют его. Ответ не считается завершённым, пока приложение не запущено, не видно пользователю, не сделан коммит и не отправлен сигнал.

## Снимки экрана (средство для Computer Vision)

Для отладки визуальных проблем (отступы, выравнивание, цвета, перекрытия) приложение имеет встроенную систему скриншотов через нативный API egui 0.37 (`ctx.request_screenshot`).

### Как использовать

1. В меню приложения выбрать **Вид → Снимок экрана**.
2. Снимок сохраняется в папку `screenshots/screenshot_<unix_ts>.png` рядом с исполняемым файлом.
3. Результат отображается в строке статуса и ленте событий приложения.

### Как это реализовано (для агентов)

- `crates/polygram/src/app/mod.rs`: поля `screenshot_requested: bool` и `screenshot_result: Arc<Mutex<Option<Result<PathBuf, String>>>>` в `PolygramApp`.
- `crates/polygram/src/main.rs`: в `ui()` обрабатывается `screenshot_requested` — вызывается `ctx.request_screenshot(|image| { ... })`, который получает `Arc<egui::ColorImage>` текущего кадра, конвертирует в `image::RgbaImage` и сохраняет через `image::RgbaImage::save()`. Вспомогательная функция `save_screenshot()` в том же файле.
- `crates/polygram/src/menu.rs`: пункт меню `Вид → Снимок экрана` устанавливает `app.screenshot_requested = true`.

### Важные моменты

- Снимок делается только содержимого egui-окна приложения, не всего экрана — нет утечек конфиденциальных данных со сторонних окон.
- Зависимость `image = "0.25"` уже есть в `crates/polygram/Cargo.toml`.
- egui версия 0.37 — `ViewportCommand::Screenshot` callback-based (см. PR #8489). Старый способ через `Event::Screenshot` больше не используется.
- Скриншот полезен для калибровки отступов, выравнивания треугольников/ромбов, проверки цветов и перекрытия элементов.
