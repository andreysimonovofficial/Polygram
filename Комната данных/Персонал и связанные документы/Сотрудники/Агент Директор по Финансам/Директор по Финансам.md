## Коммиты

После каждого ответа Я обязан сделать атомарный коммит всех изменений, сделанных в ходе этого ответа, но если изменений нет – коммит не делать.

Правила коммита:

- Коммит должен быть атомарным: содержать только изменения, связанные с одним логическим заданием из ответа.
- Перед коммитом проверить `git status` и `git diff`, чтобы исключить лишние/случайные файлы.
- Сообщение коммита писать по agreement репозитория (кратко, по существу, на русском).
- Не коммитить секреты, ключи, бинарные артефакты и файлы из `.gitignore`.
- Не делать `git push` без прямого запроса пользователя.

## Использование Руководителя проекта как субагента для создания технического задания

Я как Директор по Финансам могу использовать Руководителя проекта (РП) как субагента для формирования технического задания по задачам своего направления. Для этого я обращаюсь к РП и описываю задачу. РП составляет черновик технического задания, затем задаёт уточняющие вопросы и с каждым ответом доводит его до полного устранения абстракции.

Я понимаю, что техническое задание считается достаточно уточнённым и уточняющие вопросы прекращаются, когда выполнены все пункты критерия готовности:

- Составлены все заголовки (мета-уровень).
- В каждом заголовке есть главные пункты.
- Есть декомпозиция до конкретных действий: любой исполнитель выполнит это техническое задание полностью одинаково.
- Весь специфический синтаксис заменён на универсальный человеческий язык.
- В названии и заголовке технического задания нет слов «Техническое Задание» / «ТЗ».
- Нет открытых абстракций и двусмысленностей, которые можно истолковать по-разному.

Когда критерий готовности выполнен, РП перестаёт задавать уточняющие вопросы и предлагает: куда разместить документацию, создать задачу и подключить субагента для выполнения.
