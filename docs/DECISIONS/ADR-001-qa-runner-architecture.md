# ADR-001: Инфраструктура QA-агента (Observe → Think → Act → Verify)

## Статус
Предложено

## Контекст
Для автоматизации QA-тестирования приложения Polygram требуется инфраструктура, позволяющая агенту:
1. **Наблюдать** (Observe) — делать скриншоты окна приложения
2. **Думать** (Think) — принимать решения на основе скриншотов через VLM
3. **Действовать** (Act) — выполнять действия мышью/клавиатурой в окне приложения
4. **Верифицировать** (Verify) — проверять результат действия через скриншот после

До этого момента в приложении уже реализована базовая инфраструктура виртуального ввода (`VirtualInputState`, команды `VirtualMouseDown/Up`, `VirtualKeyDown/Up`, `VirtualWheel`, `VirtualDrag`, `inject_virtual_input()`), а также механизм скриншотов через `ctx.request_screenshot()`. Однако не былоห jednakоркестратора цикла QA, клиента VLM, DSL сценариев и модуля верификации.

## Решение
Создан модуль `app/qa/` в crate `polygram` со следующими компонентами:

### scenario.rs
DSL для описания сценариев QA в формате YAML. Определяет `QaScenario` (имя + шаги), `QaStep` (инструкция, подсказка типа действия, ожидание), `QaAction` (click, drag, key_down, key_up, wheel, wait), `QaVerdict` (success/failure/uncertain).

### runner.rs
`QaRunner` — оркестратор цикла Observe → Think → Act → Verify. Выполняет шаги сценария по очереди:
1. Делает скриншот до действия (`ctx.request_screenshot`)
2. Отправляет скриншот + инструкцию в VLM, получает `QaAction`
3. Выполняет действие через HTTP API (`virtual_mouse_*`, `virtual_key_*`, `virtual_wheel`)
4. Делает скриншот после действия
5. Верифицирует результат (сравнение ревизии состояния)

### vision.rs
`VlmClient` — HTTP клиент к VLM API (OpenAI-совместимый). Отправляет скриншот (base64 PNG) + инструкцию, получает JSON с действием.

### actuator.rs
`Actuator` — переводит `QaAction` в HTTP команды к `polygram-api` (`POST /api/commands`).

### verifier.rs
`Verifier` — проверяет результат шага через `/api/snapshot` (сравнение ревизии до/после).

### report.rs
`ReportGenerator` — формирует отчёты заказчику в требуемом формате:
«Я нажал на кнопку X. Смотри, что получилось: (скриншот). Это то, что ты ожидал?»
«Да, ожидание подтверждено» / «Нет, ожидание не подтверждено».

## Интеграция
- `QaRunner` хранится в `PolygramApp.qa` (поле типа `QaRunner`)
- UI панели QA агента добавляются в основной цикл `main.rs` (окно "QA Агент")
- Все скриншоты сохраняются в `screenshots/` и дублируются в `last_status` / `event_log`
- VLM конфигурируется через UI (endpoint, модель, API ключ)

## Альтернативы, которые были рассмотрены
1. **Вынести QA Runner в отдельный процесс** — отвергнуто,因为需要 прямой доступ к `egui::Context` для `request_screenshot()`
2. **Использовать xcap + enigo вместо egui API** — отвергнуто, так как приложение уже имеет встроенную инфраструктуру виртуального ввода через egui события
3. **Запускать QA Runner в API сервере** — отвергнуто, так как API сервер не имеет доступа к GUI окну egui

## Последствия
- Добавлены новые зависимости: `serde_yaml`, `base64`, `thiserror`
- Изменена структура `PolygramApp` (добавлено поле `qa: QaRunner`)
- Добавлен новый модуль `app/qa/` с 6 файлами
- Требуется настройка VLM endpoint для полноценной работы (без неё runner возвращает ошибку "VLM не сконфигурирован")
- Все публичные элементы документированы с `///` комментариями
